# Терминология

`Узел` — самостоятельный участник сетевого общения в рамках настоящего протокола. Узлом может быть клиент или сервер.

`Запрос` — логически обособленное сообщение согласно структуре кадра и формата конкретной версии, которое узел выполняет в рамках логической операции.

Запрос может быть:
- `инициирующим` — первым в структуре запрос-ответ.
- `ответным` — вторым в структуре запрос-ответ.

`Кадр` — обобщённая структура, содержащая данные, достаточные для корректной передачи запроса.

# Основная структура кадра

```text
| Magic bytes (2 bytes) | Version (1 byte) | Headers | Body | Checksum (4 bytes) |
```

Где:

- `Magic bytes` — уникальная последовательность, обозначающая, что настоящий кадр относится к протоколу Ignicula (0A DB).
- `Version` — версия протокола (от 0 до 255).
- `Headers` — служебные данные и флаги, определяемые версией протокола (далее также — заголовки).
- `Body` — основные данные сообщения.
- `Checksum` — контрольная сумма кадра. Конкретные реализации сами определяют, что именно покрывает контрольная сумма.

Для **всех** полей и сообщений по умолчанию используется порядок байтов big-endian.

# Установление общей версии

Независимо от реализации, любое подключение начинается со служебного кадра версии 0 (далее — Hello-запрос) следующего формата:

```text
| 0A DB | 00 | Version Len (1 byte) | Version 1 | Version 2 | ...  | Version N | CheckSum |
```

Где:

- `Version Len` — количество поддерживаемых версий протокола узлом.
- `Version N` — конкретная поддерживаемая версия.

В основной структуре кадра поле Headers представлено одним полем Version Len. Versions представлены как Body.

Для Checksum используется алгоритм `CRC-32/XFER` (poly=`0x000000AF`, init=`0`, refin=`false`, refout=`false`, xorout=`0`, check=`0xBD0BE338`). Checksum покрывает весь кадр, не считая себя.

Кадр занимает ровно `8 + Version Len` байтов: 2 байта magic, 1 байт версии, 1 байт Version Len, Version Len байтов версий и 4 байта checksum.

**Примечание автора**: дублирование версий допускается, но крайне нежелательно. Повтор номера игнорируется. Версия 0 не является рабочей и в списке поддерживаемых версий не учитывается.

## Алгоритм установления соединения

1. Клиент устанавливает TCP-соединение с сервером. TLS или иное шифрование сетевого трафика опциональны и зависят от конкретной реализации сервера.
2. Клиент отправляет Hello-запрос, указывая поддерживаемые версии.
3. Сервер отвечает сообщением с таким же форматом со своими поддерживаемыми версиями.
4. Клиент запоминает версии, поддерживаемые и клиентом, и сервером, и может общаться, используя только их.
5. Клиент и сервер действуют дальше согласно версии протокола.

Если клиент не поддерживает ни одну версию, которую поддерживает сервер, соединение не может быть установлено, клиент должен разорвать соединение, в противном случае сервер разорвёт его через некоторое конечное время.

Примеры Hello-запросов от клиента к серверу и обратно:

```text
Клиент -> Сервер

Hex-версия:

0A DB 00 03 01 02 03 6E 38 99 00

Расшифровка:
	Version: 0 (Hello)
	Versions: 1, 2, 3


Сервер -> Клиент

Hex-версия:

0A DB 00 04 01 04 07 0B 3B 78 5D 98

Расшифровка:
	Version: 0 (Hello)
	Versions: 1, 4, 7, 11

Общие версии: 1
```

Узел читает ровно `8 + Version Len` байтов одного Hello-кадра. Если версий пришло меньше, чем заявлено, соединение разрывается. Байты после кадра относятся к следующему сообщению.

# Версии

**Примечание автора**: версия 0 не является самостоятельной рабочей версией и используется только для Hello-запросов. Если клиент отпраялет кадр неподдерживаемой сервером версии, то сервер обязан закрыть соединение.

### Типы данных

Ниже приведены коды типов данных и форматы их записей. Узлы должны гарантировать, что данные соответствуют требованиям указанных типов данных.

#### Последовательность байтов

Код: 0

Пример: 0A 12 33 45

Особенности: -

Проверка соответствия:
1. Реальная длина соответствует заявленной.

Формат записи:

```text
| Value Len (4 bytes) | Value |
```

Где:

- `Value Len` — длина байтовой последовательности.
- `Value` — байтовая последовательность.

Алгоритм кодирования:
1. Внести длину байтовой последовательности.
2. Внести байтовую последовательность.

Алгоритм декодирования:
1. Прочитать первые 4 байта — Value Len.
2. Прочитать следующие Value Len байтов.

Пример кодирования-декодирования:

```text
Hex-версия: 00 00 00 04 0A 12 33 45

Расшифровка:
	Value Len: 4
	Value: 0A 12 33 45
```

#### Типизированный массив

Код: 1

Пример: {1, 2, 3}

Особенности: каждое Value должно быть раскрыто для типов "[Последовательность байтов](#последовательность-байтов)", "[Типизированный массив](#типизированный-массив)", "[Нетипизированный массив](#нетипизированный-массив)", "[Строка](#строка)", "[JSON](#json)" как структура, описанная в каждом указанном типе.

Проверка соответствия:
1. Указанная длина массива соответствует реальной.
2. Каждый элемент соответствует заявленному типу.

Формат записи:

```text
| Array Len (4 bytes) | Value Type (1 byte) | Value 1 | Value 2 | ... | Value N |
```

Где:

- `Array Len` — количество элементов.
- `Value Type` — тип элемента массива.
- `Value N` — элементы массива.

Алгоритм кодирования:
1. Внести количество элементов массива.
2. Один раз внести тип элементов.
3. Внести все элементы последовательно, кодируя их согласно их типу.

Алгоритм декодирования:
1. Прочитать первые 4 байта — Array Len.
2. Прочитать 1 байт — Value Type.
3. Декодировать элементы последовательно согласно их алгоритму декодирования, проверяя каждый элемент на соответствие его типу.

Пример кодирования-декодирования:

```text
Hex-версия: 00 00 00 02 03 00 00 00 00 00 00 00 01 00 00 00 00 00 00 00 02

Расшифровка:
	Array Len: 2
	Value Type: int
	Value 1: 1
	Value 2: 2
```

#### Нетипизированный массив

Код: 2

Пример: {1, "hello world", 12.3}

Особенности: каждое Value должно быть раскрыто для типов "[Последовательность байтов](#последовательность-байтов)", "[Типизированный массив](#типизированный-массив)", "[Нетипизированный массив](#нетипизированный-массив)", "[Строка](#строка)", "[JSON](#json)" как структура, описанная в каждом указанном типе.

Проверка соответствия:
1. Указанная длина массива соответствует реальной.
2. Каждый элемент соответствует заявленному типу этого элемента.

Формат записи:

```text
| Array Len (4 bytes) | Value 1 Type (1 byte) | Value 1 | Value 2 Type (1 byte) | Value 2 | ... | Value N |
```

Где:

- `Array Len` — количество элементов.
- `Value Type N` — тип элемента массива номер N.
- `Value N` — элемент массива номер N.

Алгоритм кодирования:
1. Внести количество элементов массива.
2. Внести тип элемента.
3. Внести элемент согласно алгоритму кодирования его типа.
4. Повторить шаги 2–3 до конца элементов.

Алгоритм декодирования:
1. Прочитать первые 4 байта — Array Len.
2. Прочитать 1 байт — Value Type.
3. Декодировать и проверить элемент согласно его типу.
4. Повторить шаги 2–3 до конца элементов.

Пример кодирования-декодирования:

```text
Hex-версия: 00 00 00 03 03 00 00 00 00 00 00 00 01 06 00 00 00 0B 68 65 6C 6C 6F 20 77 6F 72 6C 64 05 40 28 99 99 99 99 99 9A

Расшифровка:
	Array Len: 3
	Value 1:
		Value Type: int
		Value: 1
	Value 2:
		Value Type: string
		Value:
			Value Len: 11
			Value: hello world
	Value 3:
		Value Type: float
		Value: 12.3
```

#### Число с плавающей точкой

Код: 5

Пример: 31.42

Особенности: положительное значение лежит в границах от 2.2250738585072014e-308 до 1.7976931348623157e+308. Отрицательное значение лежит в границах от -1.7976931348623157e+308 до -2.2250738585072014e-308. Число кодируется в формате IEEE 754.

Проверка соответствия: отсутствует.

Формат записи:

```text
| Value (8 bytes) |
```

Где:

- `Value` — значение числа в формате IEEE 754.

Алгоритм кодирования:
1. Преобразовать число в байтовую последовательность согласно формату IEEE 754.
2. Внести байтовую последовательность.

Алгоритм декодирования:
1. Прочитать первые 8 байтов.
2. Преобразовать прочитанную байтовую последовательность согласно формату IEEE 754.

Пример кодирования-декодирования:

```text
Hex-версия: 40 28 DC 28 F5 C2 8F 5C

Расшифровка:
	Value: 12.43
```

### Ошибки

Ниже приведены коды ошибок и возвращаемые поля Details.

Примечание: иные коды резервные: их можно использовать в частной реализации настоящего протокола, либо они будут дополнены позднее в этой версии.

#### No Hello

Код ошибки: 0

Примеры:
1. Клиент после подключения не прислал Hello-запрос.

Причина: несогласование версий, отсутствие Hello-запроса.

Особенности: эта ошибка не отправляется клиенту, сохраняется только в логах. Соединение разрывается.

Как исправить: после установления TCP-соединения отправить Hello-запрос.

Структура Details: -

#### Command Not Implemented

Код: 1

Примеры:
1. Клиент отправляет Delete-запрос, но сервер не реализован обработку этой команды.

Причина: сервер не реализовал логику обработки зароса указанной команды.

Особенности: отсутсвует.

Как исправить: не использовать текущий метод для работы с сервером.

Структура Details: -

#### Unexpected Command

Код: 2

Примеры:
1. Клиент присылает Read в ответ на Ping от сервера.

Причина: неожиданная команда. Принимающий узел ожидал другую команду.

Особенности: -

Как исправить: отправить новую команду, которую ожидает принимающий узел.

Структура Details:

```text
| Expected Command (1 byte) |
```

Где:

- `Expected Command` — ожидаемая команда. Принимает значения от 0 до 255.

#### Unsupported Command

Код: 3

Примеры:
1. Клиент отправил кадр с командой 8.

Причина: неподдерживаемая команда. Указанная команда не входит в список команд текущей версии.

Особенности: -

Как исправить: использовать команды из текущей версии протокола или перейти на другую версию, где такая команда поддерживается (если такая версия существует и поддерживается клиентом и сервером).

Структура Details: -

#### Requests Conflict

Код: 4

Примеры:
1. Клиент отправляет запрос с Request ID 1 и сразу новый с Request ID 1.

Причина: принят запрос с Request ID, который уже зарегистрирован у обрабатывающего узла.

Особенности: первый запрос (в порядке времени получения) не прерывается. Второй запрос не обрабатывается (возвращается ошибка). Ответ на первый запрос должен прийти в обычном порядке.

Как исправить: повторить запрос с другим Request ID.

Структура Details: -

#### Unsupported Compression

Код: 5

Примеры:
1. Клиент или сервер использует алгоритм сжатия, не поддерживаемый другим узлом.

Причина: неподдерживаемый алгоритм сжатия. Указанный алгоритм не поддерживается принимающей стороной.

Особенности: —

Как исправить: отправить запрос с поддерживаемым принимающим узлом алгоритмом.

Структура Details: -

#### Body Limit Is Exceeded

Код: 6

Примеры:
1. Клиент отправил запрос с Body Len = 10 при ограничении сервера на размер сообщения в 8 байтов.

Причина: размер Body превышает установленное сервером ограничение на размер тела.

Особенности: возможна десинхронизация.

Как исправить: переподключиться при разрыве соединения, уменьшить размер данных или использовать сжатие.

Структура Details:

```text
| Current Body Size Limit (4 bytes) |
```

Где:

- `Current Body Size Limit` — текущее ограничение по размеру тела. Принимает значения от 0 до 4 294 967 295.

#### Mismatched CheckSum

Код: 7

Примеры:
1. Клиент прислал запрос с повреждёнными Headers или Body.
2. Клиент прислал запрос с Body Len = 8, хотя реальная длина составляет 9 байтов (при лимите сервера на размер Body в 12 байтов).

Причина: контрольная сумма кадра не совпадает с заявленной.

Особенности: возможна десинхронизация, если ошибка в Body Len.

Как исправить: переподключиться при разрыве соединения, отправить запрос с корректным Checksum.

Структура Details: -

#### Internal Error

Код: 8

Примеры:
1. Сервер вышел за пределы массива и данная ошибка не обработана.

Причина: необработанная ошибка внутри сервера.

Особенности: может быть что угодно.

Как исправить: см. логи.

Структура Details: -

#### Malformed Value

Код: 9

Примеры:
1. Структура JSON-документа нарушена.

Причина: содержимое значения не соответствует формату своего типа.

Особенности: -

Как исправить: отправить запрос с корректным указанием типа данных.

Структура Details:

```text
| Info Message |
```

Где:
- `Info Message` — текстовое описание ошибки в UTF-8 формате. Сообщение может отсутствовать. Занимает весь остаток Details.

#### Not Found

Код: 10

Примеры:
1. Клиент отправил Read-запрос с ключом, которого нет у сервера.

Причина: значение по ключу Key не найдено.

Особенности: этот код обозначает отсутствие значения по ключу. Не прерывает операции в батче.

Как исправить: исправление не требуется. Дальнейшие действия определяются бизнес-логикой клиента.

Структура Details: -

#### Prohibited Compression

Код: 11

Примеры:
1. Клиент отправил Ping-запрос со сжатием.

Причина: используется сжатие в запросах, где это запрещено.

Особенности: —

Как исправить: отправить запрос без сжатия.

Структура Details: -

#### Request Interrupted

Код: 12

Примеры:
1. Сервер выполнял запрос, но его принудительно выключают.
2. Во время выполнения Batch-запроса с флагом "Прерывание при ошибке", установленным в 1, одна из операций не выполнена из-за ошибки. В таком случае ошибка будет выведена в соответствующий Result Body.

Причина: сервер зарегистрировал запрос, но не может его выполнить из-за прерывания выполнения.

Особенности: -

Как исправить: проверить доступность сервера. В случае батча проверить ошибку, вызвавшую прерывание последующих операций.

Структура Details: -

#### Batch Limit Is Exceeded

Код: 13

Примеры:
1. Клиент отправил Batch-запрос, в который заложил 10 операций, при ограничении сервера в 8 операций в одном батче.

Причина: значение Requests Len превышает ограничение сервера на количество операций в одном батче.

Особенности: -

Как исправить: разделить батч на несколько отдельных запросов.

Структура Details:

```text
| Current Batch Size Limit (4 bytes) |
```

Где:

- `Current Batch Size Limit` — текущее ограничение по количеству операций в Batch-запросе. Принимает значения от 0 до 4 294 967 295.

#### Unexpected Command In Batch

Код: 14

Примеры:
1. Клиент отправил Batch-запрос, где для запроса с номером 2 указал команду Handshake.

Причина: значение Command одного из Request не является Read, Write, Delete.

Особенности: -

Как исправить: убрать запрос из батча. Отправить отдельно по необходимости.

Структура Details:

```text
| Request Number (4 bytes) |
```

Где:

- `Request Number` — номер запроса с некорректным Command.

#### Invalid Request ID

Код: 15

Примеры:
1. Клиент отправил Handshake-запрос с Request ID = 1.
2. Клиент отправил Read-запрос с Request ID = 0.

Причина: используется RequestID, не предусмотренный для данного запроса.

Особенности: -

Как исправить: сменить Request ID для данного запроса.

Структура Details: -

#### Unauthorized

Код: 16

Примеры:
1. Клиент отправил Handshake-запрос с неверным логином и/или паролем.

Причина: неверный логин и/или пароль в Handshake-запросе.

Особенности: -

Как исправить: ввести корректные логин и пароль.

Структура Details: -

#### Restricted Request

Код: 17

Примеры:
1. Клиент отправил Read-запрос для данных, к которым у него нет доступа.

Причина: для текущего клиента нет доступа к указанной команде и Body.

Особенности: -

Как исправить: сообщить системному администратору или иному лицу, которое отвечает за политики прав доступа.

Структура Details: -


### Сжатие

Ниже приведён список алгоритмов сжатия и кодов, соответствующих им.

| Код | Алгоритм |
| --- | -------- |
| 0   | -        |
| 1   | zstd     |
| 2   | s2       |
Иные коды резервные: их можно использовать в частной реализации настоящего протокола, либо они будут дополнены позднее в этой версии.

### Headers

```text
| Command (1 byte) | RequestID (4 bytes) | Compression (1 byte) | Body Len (4 bytes) |
```

Где:

- `Command` — номер команды (см. [Command](#command)).
- `RequestID` — уникальный идентификатор запроса клиента, который узел в настоящий момент не обрабатывает.
- `Compression` — используемое для Body сжатие.
- `Body Len` — длина Body в байтах.

#### Command

Байт, обозначающий номер команды.

Существующие команды:

0. `Handshake` — первый запрос, который инициирует только клиент после Hello-запроса и в котором он передаёт сведения, необходимые для дальнейшей работы: поддерживаемые методы сжатия и т.д. Подробности см. в [Алгоритме рукопожатия](#алгоритм-рукопожатия).
1. `Answer` — ответ на запрос. Не может использоваться как самостоятельный запрос: при ответе на несуществующий запрос должна вернуться ошибка [Unexpected Command](#unexpected-command). Может использоваться и клиентом, и сервером.
2. `Read` — запрос на получение данных. Может использоваться только клиентом. Подробности см. в [Чтение данных](#алгоритм-чтения-данных).
3. `Write` — запрос на запись данных. Может использоваться только клиентом. Подробности см. в [Записи данных](#алгоритм-записи-данных).
4. `Delete` — запрос на удаление данных. Может использоваться только клиентом. Подробности см. в [Удалении данных](#алгоритм-удаления-данных).
5. `Batch` — множество запросов. Не является транзакцией. Может использоваться только клиентом. Подробности см. в [Батчи и их применение](#алгоритм-отправки-батча-запросов).
6. `Ping` — запрос на проверку доступности. Может использоваться и клиентом, и сервером. Подробности см. в [Проверке доступности](#алгоритм-проверки-сетевой-доступности).

Иные команды в текущей версии резервные и могут использоваться конкретными реализациями этой версии протокола. В противном случае на запросы с резервными командами нужно отвечать ошибкой [Unsupported Command](#unsupported-command).

#### Request ID

Уникальный для текущего подключения идентификатор от 0 до 4 294 967 295. Используется для асинхронной работы протокола.

Значение 0 используется только для Handshake и Answer на Handshake.

#### Compression

Значение от 0 до 255. Используется для обозначения алгоритма, используемого для сжатия Body. 0 обозначает отсутствие сжатия. Список поддерживаемых алгоритмов см. в [Сжатие](#сжатие).

#### Body Len

Значение от 0 до 4 294 967 295 (4 ГиБ). Используется для обозначения размера Body (после сжатия, если оно используется). Принимающая сторона читает ровно Body Len + 4 байта (контрольная сумма).

### Body

Содержит данные запроса и зависит от Command. Если используется сжатие, после проверки контрольной суммы нужно выполнить обратное преобразование согласно алгоритму сжатия.

### CheckSum

Проверяет целостность кадра. Покрывает весь кадр, не включая себя. Используемый алгоритм — Castagnoli (CRC-32C). Если Body сжато, контрольная сумма проверяется до обратного преобразования согласно алгоритму сжатия.

### Алгоритм рукопожатия

Клиент, решивший установить соединение с сервером, должен выполнить процедуру рукопожатия.

#### Поднятие соединения

См. [Алгоритм установления соединения](#алгоритм-установления-соединения).

#### Отправка Handshake-запроса

Клиент отправляет Handshake-запрос, содержащий следующие заголовки (Headers):

- `Command` — 0
- `RequestID` — 0
- `Compression` — 0
- `Body Len` — зависит от реальной длины Body

В Body клиент передаёт данные в следующем формате:

```text
| Login Len (4 bytes) | Login | Hash (32 bytes) | Supported Compressions Len (1 byte) | Compression 1 | Compression 2 | ... | Compression N |
```

Где:

- `Login Len` — длина логина для подключения.
- `Login` — логин для подключения. Представляет собой строку в формате UTF-8.
- `Hash` — хеш пароля для подключения. В качестве хеш-функции используется Argon2id.
- `Supported Compressions Len` — количество поддерживаемых методов сжатия (см. [Сжатие](#сжатие)). Принимает значения от 0 до 255.
- `Compression N` — поддерживаемые клиентом алгоритмы сжатия.

**Примечание автора**: сервер может поддерживать анонимные соединения. В таком случае Login Len становится равным 0, а Hash заполняется нулевыми байтами.

Пример Handshake-запроса с поддерживаемыми алгоритмами Zstd и S2:

```text
Hex-версия:

0A DB 01 00 00 00 00 00 00 00 00 00 2B 00 00 00 04 75 73 65 72 01 02 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 02 01 02 7A 39 15 BF

Расшифровка:
	Version: 1
	Command: Handshake
	Request ID: 0
	Compression: -
	Login: user
	Hash: 0x01 0x02 0x00 ... 0x00
	Supported compression algorithms: Zstd, S2
	CheckSum: 7A 39 15 BF
```

#### Ответ сервера

Сервер, получив запрос, проверяет его и разбирает.

Возможны два сценария:

1. Правильный запрос

В таком случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — 0
- `Compression` — 0
- `Body Len` — зависит от реальной длины Body

В Body сервер передаёт данные в следующем формате:

```text
| 01 | 00 | Supported Compressions Len | Compression 1 | Compression 2 | ... | Compression N | Granted Versions Len | Version 1 | Version 2 | ... | Version N |
```

Где:

- `Supported Compression Len` — количество поддерживаемых методов сжатия из списка, предоставленного клиентом. Принимает значения от 0 до 255.
- `Compression N` — поддерживаемые сервером алгоритмы сжатия.
- `Granted Versions Len` — количество версий, которые сервер позволяет использовать без повторной авторизации. Принимает значения от 0 до 255.
- `Version N` — версия, к которой предоставлен доступ без повторной авторизации.

Пример Answer-запроса с поддержкой Zstd и доступом к версии 1:

```text
Hex-версия:
0A DB 01 01 00 00 00 00 00 00 00 00 06 01 00 01 01 01 01 52 6E 3E 35

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 0
	Compression: -
	Result: OK
	Responded To: Handshake
	Supported compression algorithms: Zstd
	Granted versions: 1
	CheckSum: 52 6E 3E 35
```

2. Запрос с проблемами

В этом случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — 0
- `Compression` — 0
- `Body Len` — зависит от реальной длины Body

В Body клиент передаёт данные в следующем формате:

```text
| 00 | Error Code (2 bytes) | Traceback ID (16 bytes) | Details |
```

Где:

- `Error Code` — код ошибки. Принимает значения от 0 до 65 535. Подробности см. в [Ошибках](#ошибки)
- `Traceback ID` — уникальный идентификатор ошибки.
- `Details` — детальное описание ошибки, зависящее от номера ошибки.

**Примечание автора**: здесь и далее в примерах Traceback ID интерпретируется как бинарный UUID.

Пример Answer-запроса с ошибкой [Unexpected Command](#unexpected-command), вызванной тем, что клиент после Hello-запроса не прислал Handshake-запрос:

```text
Hex-версия:

0A DB 01 01 00 00 00 00 00 00 00 00 14 00 00 02 6B AE 36 80 76 95 47 42 92 AF 0A 6F EC 33 98 25 00 F0 8E 28 51

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 0
	Compression: -
	Result: NOT OK
	Error:
		Unexpected Command
		Traceback ID: 6bae3680-7695-4742-92af-0a6fec339825
		Details:
    		Expected Command: Handshake
	CheckSum: F0 8E 28 51
```

### Алгоритм чтения данных

#### Отправка Read-запроса

Клиент отправляет Read-запрос, содержащий следующие заголовки (Headers):

- `Command` — 2
- `Request ID` — уникальный: в текущий момент не должно быть выполняющихся запросов с тем же значением
- `Compression` — опционально, поддерживаемый сервером алгоритм
- `Body Len` — зависит от реальной длины Body

В Body клиент передаёт данные в следующем формате:

```text
| Key |
```

Где:

- `Key` — бинарная последовательность, соответствующая ключу, по которому будет происходить поиск.

Указывать длину Key не нужно: Key занимает всё тело Body.

Пример Read-запроса без сжатия с Request ID = 1 и ключом (Key) = "some-key":

```text
Hex-версия:

0A DB 01 02 00 00 00 01 00 00 00 00 08 73 6F 6D 65 2D 6B 65 79 E1 5A 14 00

Расшифровка:
	Version: 1
	Command: Read
	Request ID: 1
	Compression: -
	Key: some-key
	CheckSum: E1 5A 14 00
```

#### Ответ сервера

Сервер, получив запрос, проверяет его и разбирает.

Возможны три сценария:

1. Правильный запрос, данные существуют.

В таком случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — тот же, что и у Read-запроса
- `Compression` — опционально, поддерживаемый клиентом алгоритм
- `Body Len` — зависит от реальной длины Body

В Body сервер передаёт данные в следующем формате:

```text
| 01 | 02 | Value Type (1 byte) | Value |
```

Где:

- `Value Type` — тип значения. См. в [Типы данных](#типы-данных).
- `Value` — значение в формате его типа.

Пример Answer-запроса без сжатия с Request ID = 1 и значением (Value) = "some-data":

```text
Hex-версия:

0A DB 01 01 00 00 00 01 00 00 00 00 10 01 02 06 00 00 00 09 73 6F 6D 65 2D 64 61 74 61 5E 79 B8 83

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 1
	Compression: -
	Result: OK
	Responded To: Read
	Data:
		Type: string
		Value: some-data
	CheckSum: 5E 79 B8 83
```

Пример Answer-запроса без сжатия с Request ID = 10 и значением (Value) = {1, "hello world", 2.1}:

```text
Hex-версия:

0A DB 01 01 00 00 00 0A 00 00 00 00 29 01 02 02 00 00 00 03 03 00 00 00 00 00 00 00 01 06 00 00 00 0B 68 65 6C 6C 6F 20 77 6F 72 6C 64 05 40 00 CC CC CC CC CC CD 34 E8 E0 75

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 10
	Compression: -
	Result: OK
	Responded To: Read
	Data:
		Type: untyped array
		Value:
			1:
				Type: int
				Value: 1
			2:
				Type: string
				Value: hello world
			3:
				Type: float
				Value: 2.1
	CheckSum: 34 E8 E0 75
```

2. Правильный запрос, данных нет.

В таком случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — тот же, что и у Read-запроса
- `Compression` — 0
- `Body Len` — зависит от реальной длины Body

В Body сервер передаёт данные в следующем формате:

```text
| 00 | 00 0A | TracebackID (16 bytes) |
```

что соответствует сообщению с ошибкой [Not Found](#not-found) и идентификатором Traceback.

Пример Answer-запроса с Request ID = 1:

```text
Hex-версия:

0A DB 01 01 00 00 00 01 00 00 00 00 13 00 00 0A F1 38 9C 1F A2 2F 40 82 A2 79 D2 01 7C 60 F8 20 88 EE CC AA

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 1
	Compression: -
	Result: NOT OK
	Error:
		Not Found
		Traceback ID: f1389c1f-a22f-4082-a279-d2017c60f820
		Details: -
	CheckSum: 88 EE CC AA
```

3. Неправильный запрос или внутренняя ошибка.

В таком случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — тот же, что и у Read-запроса
- `Compression` — 0
- `Body Len` — зависит от реальной длины Body

В Body сервер передаёт данные в следующем формате:

```text
| 00 | Error Code (2 bytes) | Traceback ID (16 bytes) | Details |
```

Где:

- `Error Code` — код ошибки. Принимает значения от 0 до 65 535. Подробности см. в [Ошибках](#ошибки).
- `Traceback ID` — уникальный идентификатор ошибки.
- `Details` — детальное описание ошибки, зависящее от номера ошибки.

Пример Answer-запроса с Request ID = 1 и ошибкой [Internal Error](#internal-error):

```text
Hex-версия:

0A DB 01 01 00 00 00 01 00 00 00 00 13 00 00 08 A5 18 B2 C1 CC 27 49 27 94 09 6A 10 15 DA 67 B1 9C 90 B4 33

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 1
	Compression: -
	Result: NOT OK
	Error:
		Internal Error
		Traceback ID: a518b2c1-cc27-4927-9409-6a1015da67b1
		Details: -
	CheckSum: 9C 90 B4 33
```

### Алгоритм удаления данных

#### Отправка Delete-запроса

Клиент отправляет Delete-запрос, содержащий следующие заголовки (Headers):

- `Command` — 4
- `Request ID` — уникальный: в текущий момент не должно быть выполняющихся запросов с тем же значением
- `Compression` — опционально, поддерживаемый сервером алгоритм
- `Body Len` — зависит от реальной длины Body

В Body клиент передаёт данные в следующем формате:

```text
| Key |
```

Где:

- `Key` — бинарная последовательность, соответствующая ключу, по которому будет происходить удаление.

Указывать длину Key не нужно: Key занимает всё тело Body.

Пример Delete-запроса без сжатия с Request ID = 3 и ключом (Key) = "another-key":

```text
Hex-версия:

0A DB 01 04 00 00 00 03 00 00 00 00 0B 61 6E 6F 74 68 65 72 2D 6B 65 79 F4 C7 FF 81

Расшифровка:
	Version: 1
	Command: Delete
	Request ID: 3
	Compression: -
	Key: another-key
	CheckSum: F4 C7 FF 81
```

#### Ответ сервера

Сервер, получив запрос, проверяет его и разбирает.

Возможны два сценария:

1. Правильный запрос.

В контексте удаления не имеет значения фактическое существование ключа у сервера. Сервер не должен вызывать ошибку ([Not Found](#not-found)).

В таком случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — тот же, что и у Delete-запроса
- `Compression` — 0
- `Body Len` — зависит от реальной длины Body

В Body сервер передаёт данные в следующем формате:

```text
| 01 | 04 |
```

Пример Answer-запроса с Request ID = 3:

```text
Hex-версия:

0A DB 01 01 00 00 00 03 00 00 00 00 02 01 04 3D F3 9E F2

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 3
	Compression: -
	Result: OK
	Responded To: Delete
	CheckSum: 3D F3 9E F2
```

2. Неправильный запрос или внутренняя ошибка.

В таком случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — тот же, что и у Delete-запроса
- `Compression` — 0
- `Body Len` — зависит от реальной длины Body

В Body сервер передаёт данные в следующем формате:

```text
| 00 | Error Code (2 bytes) | Traceback ID (16 bytes) | Details |
```

Где:

- `Error Code` — код ошибки. Принимает значения от 0 до 65 535. Подробности см. в [Ошибках](#ошибки).
- `Traceback ID` — уникальный идентификатор ошибки.
- `Details` — детальное описание ошибки, зависящее от номера ошибки.

Пример Answer-запроса с Request ID = 3 и ошибкой [Internal Error](#internal-error):

```text
Hex-версия:

0A DB 01 01 00 00 00 03 00 00 00 00 13 00 00 08 CA D1 C1 02 CA C5 4D DF 9B 61 EB 00 81 8E 25 D1 4F 23 68 80

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 3
	Compression: -
	Result: NOT OK
	Error:
		Internal Error
		Traceback ID: cad1c102-cac5-4ddf-9b61-eb00818e25d1
		Details: -
	CheckSum: 4F 23 68 80
```

### Алгоритм отправки батч-запросов

#### Отправка Batch-запроса

Клиент отправляет Batch-запрос, содержащий следующие заголовки (Headers):

- `Command` — 5
- `RequestID` — уникальный: в текущий момент не должно быть выполняющихся запросов с тем же значением
- `Compression` — опционально, поддерживаемый сервером алгоритм
- `Body Len` — зависит от реальной длины Body

В Body клиент передаёт данные в следующем формате:

```text
| Flags (1 byte) | Requests Len (4 bytes) |  Request 1 | Request 2 | ... | Request N |
```

Где:

- `Flags` — флаги настройки выполнения. Подробности см. ниже.
- `Requests Len` — количество запросов в батче.
- `Request N` — запрос N. Формат запроса см. ниже.


**Флаги (Flags)**

Это настройки выполнения батча запросов. Биты флагов:

0. `Последовательность выполнения запросов`. 1 — последовательная (по порядку Request Number). 0 — параллельная.
1. `Прерывание при ошибке`. 1 — прерывание дальнейшего выполнения (вернётся ошибка [Request Interrupted](#request-interrupted) для оставшихся невыполненных запросов). 0 — возврат ошибки, остальные операции не прерываются.
2. `Возврат результата`. 1 — однократный возврат результата всех запросов. 0 — возврат результатов в порядке выполнения (не обязательно в порядке Request Number, если флаг "последовательность выполнения запросов" установлен в 0).
3. Резерв.
4. Резерв.
5. Резерв.
6. Резерв.
7. Резерв.

**Request**

Один из запросов, включённый в батч. Формат записи:

```text
| Request Number (4 bytes) | Command (1 byte) | Request Body Len (4 bytes) | Request Body |
```

Где:

- `Request Number` — уникальный номер операции в рамках текущего батча.
- `Command` — только операция Read, Delete или Write.
- `Request Body Len` — размер тела запроса.
- `Request Body` — Body, формат которого определён для Read-, Delete- и Write-запросов.

Пример Batch-запроса с двумя операциями:
- Read-запрос с Request Number = 1 и Key = "key"
- Write-запрос с Request Number = 2, Key = "another-key" и Value = "data"

Использованы следующие флаги:
- однократный возврат ответа.
- пропуск операции при ошибке.
- операции выполнять последовательно.

Headers:
- `RequestID` = 1
- `Compression` = 0

```text
Hex-версия:

0A DB 01 05 00 00 00 01 00 00 00 00 32 05 00 00 00 02 00 00 00 01 02 00 00 00 03 6B 65 79 00 00 00 02 03 00 00 00 18 00 00 00 0B 61 6E 6F 74 68 65 72 2D 6B 65 79 06 00 00 00 04 64 61 74 61 DE 84 44 1C

Расшифровка:
	Version: 1
	Command: Batch
	Request ID: 1
	Compression: -
	Flags:
		One answer
		Continue with errors
		Execute sequentially
	Requests:
		1:
			Command: Read
			Key: key
		2:
			Command: Write
			Key: another-key
			Data:
				Type: string
				Value: data
	CheckSum: DE 84 44 1C
```

#### Ответ сервера

Сервер, получив запрос, проверяет его и разбирает.

Возможны два сценария:

1. Правильный запрос. Батч принят к обработке.

В таком случае сервер отправляет Answer-запрос, содержащий следующие заголовки (Headers):

- `Command` — 1
- `RequestID` — тот же, что и у Batch-запроса
- `Compression` — опционально, поддерживаемый клиентом алгоритм
- `Body Len` — зависит от реальной длины Body

```text
| 01 | 05 | Results Len (4 bytes) | Result 1 | Result 2 | ... | Result N |
```

Где:

- `Results Len` — количество ответов в кадре.
- `Result N` — результат выполнения запроса N. Формат см. ниже.

**Result**

Один из результатов запроса из батча. Формат записи:

```text
| Request Number (4 bytes) | Result Body Len (4 bytes) | Result Body |
```

Где:

 - `Request Number` — уникальный номер операции в батче.
 - `Result Body Len` — длина Result Body.
 - `Result Body` — Body, который определён для успешных и неуспешных ответов на Read-, Delete- и Write-запросы (см. [Алгоритм чтения данных](#алгоритм-чтения-данных), [Алгоритм записи данных](#алгоритм-записи-данных), [Алгоритм удаления данных](#алгоритм-удаления-данных)).

**Примечание автора**: в случае, если флаг "Возврат результата" установлен в 1, то Answer-запрос будет ровно один. В противном случае сервер может "возвращать результаты" по одному, используя ту же структуру, или несколькими последовательностями. Клиент обязан сам следить за количеством полученных результатов по общему количеству Requests Len, отправленному клиентом, и количеству Results Len, отправленному сервером. Сервер обязан дать ответ на все запросы в батче.

Пример Answer-запроса без сжатия на запрос с Request ID = 1 и установленными флагами:

### Таймауты и heartbeat

Протокол не фиксирует интервал проверки сетевой доступности командой [Ping](#алгоритм-проверки-сетевой-доступности) и таймаут ожидания.

Рекомендации:
- Для сервера:
	- отправлять Ping каждые 30 секунд, если от клиента не было запросов.
	- разрывать соединение, если клиент не подал признаков активности: ответ на Ping-запрос или иной запрос в течение 100 секунд после отправки первого Ping-запроса.
- Для клиента:
	- в случае простоя отправлять серверу Ping-запросы каждые 15 с.

### Переподключение

При разрыве соединения клиент может переподключиться. Все незавершённые запросы на момент разрыва считаются неуспешными: ответа на них не будет. Клиент сам решает, повторить ли запрос.

### Шифрование

Настоящий протокол не фиксирует конкретный алгоритм шифрования и оставляет реализацию на усмотрение пользователей.

Если сервер использует шифрование, клиент обязан подготовить защищённое соединение до отправки Hello-запроса.

В настоящем протоколе рекомендуется использовать TLS для обеспечения безопасности подключения.

### Ограничения

Если для поля кадра ограничения не оговорены, сервер вправе накладывать свои ограничения на уровне приложения.

Текущие ограничения протокола:

- `Body Len`: 0..4 294 967 295.
- `RequestID`: 1..4 294 967 295 (значение 0 зарезервировано).
- `Version`: 0..255.
- `Requests Len`: 0..4 294 967 295.
- `Results Len`: 0..4 294 967 295.
- `Supported Compressions Len`: 0..255.
- `Supported Versions Len`: 0..255.
- `Error Code`: 0..65 535.
- `Current Body Size Limit`: 0..4 294 967 295.
- `Current Batch Size Limit`: 0..4 294 967 295.
