# Как это работает

Ignicula — бинарный протокол поверх потока байтов (обычно TCP, опционально TLS). Библиотека кодирует и разбирает кадры; сокет, хранилище и политики доступа остаются за приложением.

Полные правила — в [спецификации](specs.md). Примеры API — в [туториалах](tutorial.md).

## Жизненный цикл соединения

```text
клиент                         сервер
   |                              |
   |-------- Hello v0 ----------->|
   |<------- Hello v0 ------------|
   |   пересечение версий         |
   |-------- Handshake v1 ------->|
   |<------- Answer --------------|
   |                              |
   |   Read / Write / Delete /    |
   |   Ping / Batch  (RequestID)  |
```

1. Клиент открывает TCP (и TLS, если сервер этого требует) **до** Hello.
2. Оба узла обмениваются Hello версии 0 и берут пересечение списков. Версия 0 рабочей не является.
3. Клиент отправляет Handshake (`RequestID = 0`) с логином, хешем Argon2id и предложенными алгоритмами сжатия.
4. Сервер отвечает Handshake Answer (принятые алгоритмы сжатия и версии без повторной авторизации) или протокольной ошибкой.
5. Дальше идут рабочие команды. Один кадр — один `RequestID`. Несколько запросов могут быть в полёте одновременно.

Если общих версий нет, клиент закрывает соединение. После обрыва все незавершённые запросы считаются неуспешными.

## Кадр

Общая схема всех версий:

```text
| Magic 0A DB (2) | Version (1) | Headers | Body | Checksum (4) |
```

Порядок байтов — big-endian.

**Версия 0 (Hello).** Headers — один байт `Version Len`. Body — столько же однобайтовых номеров версий. Контрольная сумма — CRC-32/XFER по всему кадру, кроме себя. Длина кадра ровно `8 + Version Len`.

```text
| 0A DB | 00 | N | v1 .. vN | XFER |
```

**Версия 1.** Headers — команда, `RequestID`, код сжатия и длина тела.

```text
| 0A DB | 01 | Command | RequestID | Compression | Body Len | Body | CRC-32C |
```

Контрольная сумма — Castagnoli (CRC-32C) по всему кадру, кроме себя. Если Body сжато, сумма считается **до** распаковки. Принимающая сторона читает ровно `Body Len + 4` байта после заголовков.

`DecodePreamble` смотрит первые три байта и не сдвигает курсор. По `Version` выбирается декодер: `v0` или `v1`. Версию можно менять на каждом кадре — на одном соединении Hello идёт как v0, рабочие команды как v1 или другая согласованная версия.

## Асинхронность

`RequestID` multiplexит запросы на одном соединении. Значение `0` зарезервировано для Handshake и ответа на него. Повтор того же `RequestID`, пока первый запрос ещё жив, даёт Request Conflict: первый запрос продолжается, второй отклоняется.

Ответ всегда несёт тот же `RequestID`, что и запрос. Клиент сопоставляет ответы по этому полю, а не по порядку кадров.

## Типы и команды

Версия 1 кодирует значения с тегом типа: bytes, typed/untyped array, int, uint, float64 (IEEE 754), UTF-8 string, JSON.

Команды:

| Код | Имя | Кто шлёт |
| --- | --- | --- |
| 0 | Handshake | только клиент, один раз после Hello |
| 1 | Answer | любой узел, только как ответ |
| 2 | Read | клиент |
| 3 | Write | клиент |
| 4 | Delete | клиент |
| 5 | Batch | клиент |
| 6 | Ping | любой узел |

Read и Delete кладут ключ на всё тело. Write префиксирует ключ длиной и тегом типа.

## Сжатие

Код `0` — без сжатия. Спецификация задаёт zstd (`1`) и s2 (`2`); остальные коды резервные. Сжимается только Body. Handshake и Ping сжимать нельзя. Декодер получает карту компрессоров и отклоняет неизвестный код ошибкой Unsupported Compression.

Порядок на приёме: заголовки → тело + сумма → проверка CRC → распаковка → разбор команды.

## Батч

Батч — не транзакция. Внутри только Read, Write, Delete. Три флага:

- последовательность или параллель;
- прерывать ли остальные операции после ошибки;
- один общий Answer или ответы по мере готовности.

Каждый вложенный запрос имеет `Request Number` внутри батча. Ответ повторяет эти номера. Если ответы приходят несколькими кадрами, клиент суммирует `Results Len`, пока не наберёт исходный `Requests Len`.

## Ошибки

Протокольная ошибка — это Answer с кодом, `TracebackID` (16 байт) и опциональными Details. `TracebackID` связывает ответ клиенту с записью в логе сервера.

Локальные ошибки библиотеки (битый magic, EOF, неверная сумма на v0, превышение лимита сборщика) на провод не кодируются: приложение само решает, закрыть соединение или ответить протокольной ошибкой.

## Лимиты и heartbeat

Спецификация задаёт верхние границы полей (Body до 4 ГиБ, 255 версий в Hello, 255 алгоритмов сжатия). Сервер вправе сузить их. В этой библиотеке лимит тела задаётся в `NewDecoder` / `NewFrameBuilder`.

Интервал Ping не фиксирован. Рекомендация спецификации: сервер шлёт Ping каждые 30 с простоя и рвёт соединение через 100 с без ответа; клиент при простое шлёт Ping каждые 15 с.
